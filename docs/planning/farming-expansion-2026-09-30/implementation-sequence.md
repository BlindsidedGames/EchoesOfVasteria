## First playable slice

**Player flow:** Barkley's new preparation hand-in makes the first two beds available. A completed eligible adventure plant can award a Radish pack. The pack becomes a fresh discovery; returning, dying or abandoning does not revoke a committed reward. In town, the player opens Farm, plants one pack in an empty bed, sees its crop/progress, then harvests its one ready batch. Save/reload and offline time lead to the same result. A keyboard/list action performs every operation available through world clicks.

**Content boundary:** one verified recipe, two stage 1 bed bindings, one pack family, one build quest and the Farm screen. The remainder of the 17 crops and stages 2/3 stay locked/unimplemented in that development slice. No animals, planks, Construction skill, watering attendance or automatic replanting. Ordinary adventures and earned skill XP remain their own loop; repeated planting/harvesting grants no Farming XP or seed rolls.

Use stable authored IDs, provisionally `farm.original.west`, `farm.original.east`, `recipe.radish.v1`, `seed.radish` and `Farm.PrepareBeds`. They are proposals for the content manifest, not new save fields or committed asset names. Bind them to scene references, not object names or coordinates used as identities. Requirements derive from canonical TaskData, current build facts and independent seed acquisition history. Store actual work/payment receipts and batch state, not PlotUnlocked/RecipeUnlocked flags.

Radish is Farming level 1; Corn is 7. The first stage should be accessible without a Corn unlock prerequisite: recommend Barkley's preparation objective plus the existing level 1 gate. Exact material prices and its intro/offer condition need content review, not migration grandfathering. The earlier10 Log/20 Stick example remains an unmeasured prototype setting, not a chosen price. Put duration, yield, cost and seed probability in versioned authored development configuration; test with injected clocks/randomness. Do not reserve schema 4 just because an isolated migration experiment used that number.

### Proposed typed command and reward protocol

Use Oracle as coordinator/journal owner. A command carries operationId, slot/tree identity, expected batch/phase identities and a typed delta. FarmService validates against a detached candidate; SaveManager supplies authority/immutable write semantics. Current APIs need extension; this is an architecture contract, not an existing atomic transaction API.

- Town plant, harvest and build commands admit only after adventure shutdown and pending rewards drain. Adventure **seed credits** use the same save lane while a run is active, with captured attribution; do not accidentally ban all seed collection through the town-only gate.
- Assign a persisted reward sequence/identity at the run/task reward source and persist the resolved pack result with the credit. The inspected tracker stores task-type aggregates, not a ready-made durable per-completion run GUID. Freeze typed reward inputs/results before asynchronous admission; do not retain DropResolver scratch buffers. Designing/resuming that identity is order 3 work. Do not reroll a committed reward after recovery; do not persist an ever-growing per-task ledger without a reviewed checkpoint/compaction rule.
- For a positive seed outcome, enqueue a typed credit with its resolved result. Coalesce pending compatible credits behind the save lane; treat balance/discovery as committed only after authority confirmation. Keep a recoverable pending operation during the asynchronous interval and drain it on run end and lifecycle saves. Do not add a full disk write for every non-seed crop completion. Profile positive-credit serialization and batching before setting production odds.
- Capture complete current contributors, clone, validate the full delta, write, then narrowly publish affected farm/inventory/quest fields and caches into the same live tree. Coalesce autosaves and defer whole hand-in/mix/craft/conversion operations. Later unrelated skill/run changes remain intact and receive the next fresh snapshot.
- Commit seed debit + new batch together; commit all selected ready batches + final payouts + cleared beds + claim IDs together. An unresolved selected recipe blocks Harvest Ready with zero changes. A newly ready batch waits for the next command.
- Before durable success, failure leaves the prior state or a safely retained unresolved operation; after success but before publication, recovery reloads the authoritative state and never replays payout. Ambiguous authority enters existing recovery. Lifecycle drain must publish before contributor capture. Slot/import/reset cannot carry a pending command to another slot.

This protocol is deliberately more work than changing an inventory counter. It closes the exact autosave/reward/cache failure boundaries exposed by current code while keeping one writer and a bounded first farm slice.
