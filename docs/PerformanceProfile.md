# Echoes of Vasteria performance profile — 26 September 2026

This is an investigation of the current dirty workspace and live Unity runtime, not a performance certification. Measured findings, synthetic stress tests, unverified hypotheses and coverage gaps are separated below. No optimisation or gameplay rebalance was implemented.

The strongest Player-supported findings are a CPU-heavy cauldron refresh and frame-rate-dependent forging. At 3840 × 2160, native tasting with the window open raised frame p95 from 8.34 to about 13.0 ms; main-thread p95 rose from about 3.5 to 13.0 ms while GPU p95 stayed below 3.5 ms. Native 20/s forging produced 15.68–15.87 successful crafts/s at a 30 FPS cap versus 19.18/s at 144, across three repetitions each. The developed five-map Player pass mostly met its 120 FPS cap, despite occasional generation-period spikes. Large Editor costs therefore need Player validation before being treated as shipping costs.

This audit includes broad map/progression proxies, repeated UI/automation controls, targeted CPU/allocation traces, durable save/load and offline processing, plus a locally built rendered Development Player. It is **not exhaustive**: coherent natural midgame saves, long runs on four maps, deterministic accelerated combat, shipping IL2CPP, live cloud callbacks and native-memory ownership remain unmeasured.

**Forge follow-up:** [controlled Player tests](ForgePerformanceFollowup.md) did not reproduce the 67 ms Editor result. Suppressing all forge display refreshes saved only 0.23–0.37 ms of Player main-thread p95 in the clean confirmation, with no frame-p95 improvement at the cap. Read that follow-up before treating the original open/closed Editor gap as an optimisation opportunity.

## Evidence and reproduction

Captures and the complete per-scenario table are in [profiling/2026-09-26](profiling/2026-09-26/), especially [README.md](profiling/2026-09-26/README.md), [KeyResults.md](profiling/2026-09-26/KeyResults.md), [ScenarioResults.md](profiling/2026-09-26/ScenarioResults.md), [summary.csv](profiling/2026-09-26/summary.csv), and [analyse.py](profiling/2026-09-26/analyse.py). Each ordinary scenario has a raw frame CSV (losslessly stored in frame-captures.zip), a `-setup.json` containing the synchronous setup cost and initial state, and a `-meta.json` containing before/after state. The sampler records the actual resolution, VSync, cap, scale, crafting/tasting state, save sizes, object counts and collection counts. Named CPU timeline and layout probe files are separate targeted experiments.

The source was inspected through `unity-cli` and the connected Unity 6000.6.0f1 Editor. Base commit: `5c2e864f7b06e4cddf21705e54d2b177ec6578b4`; substantial existing uncommitted changes mean that commit alone does **not** reproduce this code. The original Git status is retained privately in `Library/PerformanceAudit/workspace-before.txt`.

Hardware: Ryzen 9 9950X, RTX 4080 SUPER, approximately 61.5 GiB physical RAM, Windows 11 build 26200, Direct3D 12, Ultra quality, UniversalRP. Editor Game view reports 3840 × 2160. Editor-wide timing, allocation, memory and draw counters include Editor work. A running Editor with other panels is not equivalent to a shipping player.

Ordinary steady windows warm for 5 seconds then capture 15–20 seconds. Important UI/rate comparisons have three sequential repetitions. Creation, return, death/reap, long-run continuation and deliberate UI-churn windows have their own durations and usually no warm-up; these are transition/workload captures, not steady idle samples. Percentiles use linear interpolation over each window, not pooled average FPS. The first two frame samples are excluded because metadata enumeration and the previous-frame recorder lag contaminate the boundary; the raw CSV retains them. Synchronous setup timing is reported separately. Consequently, neither the steady percentiles nor an eight-second creation window alone is a complete application cold-start measurement.

`LoadData()` restores saved rendering preferences. Earlier Editor captures generally record VSync **1**, even when the initial test requested zero. They must be read using their metadata, not labelled universally uncapped. Explicit later forge/map cap comparisons set VSync zero **after** loading. `targetFrameRate` is a request; actual frame intervals establish whether the requested cap was achieved. Frame intervals use Unity unscaledDeltaTime; wall intervals are retained as a cross-check. Main Thread time contains waits; PlayerLoop, BehaviourUpdate and targeted CPU samples provide better attribution. Available GPU recorder values are reported; missing/all-zero GPU or render-thread counters are unavailable, not zero cost.

Routine counters were collected without Deep Profile. Targeted CPU captures opened the Unity Profiler and enabled `ProfilerDriver`; earlier `cpu-*` attempts without an active Profiler yielded empty timelines and are not evidence. `timeline-*` captures include Profiler overhead and cold window activation. Their inclusive/self times locate work but must not be substituted for ordinary frame distributions. Handler wrappers and forced-layout microbenchmarks are explicitly instrumented experiments. No whole-session Deep Profile or heap snapshot was taken.

Live `GameplayStatTracker` counters supply map tasks/kills, with at most a frame of boundary uncertainty. Save-record totals do not update every frame and are deliberately excluded when live observations are absent. Successful craft counts come from `CraftingService.OnIvanXpChanged`, which fires once per successful craft; `Forge.TotalCrafts` proved stale in this scene. The first craft-observer window was partial and is marked accordingly. Tasting counts use `CauldronTotals.TotalTastings`. Every rate is per **real** second, including accelerated runs.

Cleanup and real-save verification are recorded at the end of this report.

## Measured findings and proposed work

The following are measured costs, followed by proposed changes. **No speedup from a proposed change has been measured**, because no optimisation was implemented. Estimates are opportunities to test, not promised additive gains.

1. **Cauldron window layout — high confidence in the CPU/UI cost, reproduced in the Player.** At the native 100 rolls/s, closed-window p95 frames were 11.6–12.7 ms versus 34.7–35.3 ms open, across three repetitions. PlayerLoop p95 rose from 5.1–6.0 to 26.2–26.4 ms. The same open-window penalty exists at only 10 rolls/s, making the roll count alone an inadequate explanation. The targeted timeline recorded 1090 ms of `CanvasUpdate.Layout` across 245 frames; the closed control recorded 0.029 ms across 368 frames. A forced rebuild of `Canvas/SafeArea/UnifiedWindow/TownWIndows/Cauldron_Window/Image` (1421 active descendant RectTransforms) took a median 16.12 ms over five probes. The equivalent forge subtree was about 2.03 ms. These forced rebuild costs are not per-frame normal costs, but directly reproduce the expensive hierarchy.

   Trigger paths include [CauldronWindowUI.RefreshDrinkingTexts](../Assets/Scripts/UI/CauldronWindowUI.cs#L469), [CollectionsWindowUI.OnCardGained](../Assets/Scripts/UI/CollectionsWindowUI.cs#L239) and the nested [Main scene cauldron hierarchy](../Assets/Scenes/Main.unity#L178384). Handler instrumentation measured only 58.3 ms total for 6934 collection-card callbacks over about 25 s, and 10.6 ms for 232 drinking-text refresh calls. This rejects the simple hypothesis that callback execution itself explains the 25 ms UI hitches; downstream layout is the stronger explanation. First isolate frequently changing counters/bars from the large layout subtree, cache stable layout sizes, and measure whether flattening/virtualising collection rows is necessary. Expected opportunity: recover a material fraction of the roughly 9.5 ms Player main-thread p95 difference (about 20 ms PlayerLoop difference in the Editor). These percentile differences bound the observed opportunity; they are not measured gains or a guarantee that every excess millisecond belongs to layout. Risk: responsive sizing, scrolling, localisation and tier transitions. Verify open/closed 10/100/1000 rolls/s, same layout/resolution and equal roll throughput, with before/after layout-marker and frame-percentile captures.

2. **Accelerated run generation and allocation spikes — high confidence that the cost exists, medium confidence in exact inner-method attribution.** Developed full-loadout later windows reached 32.8–40.8 ms p95 frames across the five maps, with roughly 121–201 KB/frame allocation. The focused Farmlands timeline recorded 63 generation coroutine slices totalling 314 ms inclusive (258 ms self), with a worst slice of 58.98 ms. Three `Scan` samples totalled 37.31 ms, worst 12.68 ms. Four `GC.Collect` samples totalled 105.48 ms, worst 32.16 ms; incremental collection also contributed. These are instrumented Editor measurements, not Player worst-case claims. The rendered Player runs below stayed near 8.34 ms p95, with ordinary-run worst frames 12–27 ms; do not prioritise a major generation rewrite using the Editor maxima alone.

   [SegmentedMapGenerator.CreateSegment](../Assets/Scripts/MapGeneration/SegmentedMapGenerator.cs#L202) invokes tile/decor and task generation with fixed work counts per yield; [TilemapChunkGenerator.GenerateSegmentAsync](../Assets/Scripts/MapGeneration/TilemapChunkGenerator.cs#L125) runs tile and decor passes, including per-cell decor eligibility queries. Unity's coroutine marker is attributed to the owning segmented generator, so it does not conclusively split tile, decor and procedural task work. [MoveGraph](../Assets/Scripts/MapGeneration/SegmentedMapGenerator.cs#L238) explicitly pauses pathfinding and performs a full scan on each shift. Consider time-budgeted generation slices and cached terrain/decor eligibility first; investigate graph-strip updates only with pathfinding correctness tests. Opportunity: reduce the measured tens-of-milliseconds worst slices, not necessarily total work. Risk: visible unfinished chunks, stale path nodes, ordering and density changes. Verify equal generated dimensions, task/decor counts and workload, plus repeated seam traversal, unreachable targets and return/restart cycles; do not reduce spawn density as a performance fix.

3. **UI work repeats during accelerated runs even when its panel is closed — measured allocation attribution plus a verified triggering code path.** In the focused map capture, `GameManager.Update` accounted for about 5.45 MB of allocations across 391 frames. [UpdateGenerationButtonStats](../Assets/Scripts/GameManager.cs#L303) formats statistics for all five map entries; [Update](../Assets/Scripts/GameManager.cs#L454) schedules this with `Time.time + 0.1`, with no visibility guard. At scale 4 this nominally asks for 40 refreshes per real second, capped by rendered frames, even during a run. This is an allocation/CPU scheduling issue, not a draw-call bottleneck. Refresh these texts on visible-panel/stat changes or a bounded real-time UI cadence. Expected benefit: avoid much of this attributed allocation stream while hidden; actual total-frame gain is unmeasured and likely smaller than the cauldron layout penalty. Risk: stale menu stats when reopened. Verify hidden/open counters, first-open correctness, normal/Slipstream allocation per real second and identical gameplay throughput.

4. **Alter-echo generator panel formats many labels every frame — high confidence in the measured Editor workload.** Its broad window had about 119 KB/frame allocation versus about 18 KB/frame in developed idle. A targeted timeline invoked [AlterEchoGeneratorProgressUI.Update](../Assets/Scripts/NpcGeneration/AlterEchoGeneratorProgressUI.cs#L100) 15128 times over 249 frames (about 61 rows/frame), totalling 244.9 ms inclusive / 229.8 ms self. It formats total collected, stored output, interval and card-power strings and checks buttons every frame. Cache stable rate strings and update changing text only when its displayed value changes; leave smooth progress-bar animation independent. Expected opportunity: remove a substantial fraction of the roughly 100 KB/frame panel allocation difference; measured reduction awaits implementation. Risk: stale displayed rates after card/skill/load changes. Verify those invalidation paths and a long panel-open session, not just idle numbers.

5. **Forge automation loses nominal throughput to frame scheduling — native cap results below.** Synthetic 100/s achieved about 94.0–94.6 successful crafts/s; synthetic 1000/s achieved 915.6–930.2/s with the window open and about 927.8/s closed. The closed window did not stop automation; the scenario name `forge-close-stops-auto` records a rejected hypothesis. Both forge and cauldron active reached about 41.6 ms p95 / 46.7 ms p99 frames while sustaining roughly 918 crafts and 100 tasting rolls per real second. [CraftUntilUpgradeCoroutine](../Assets/Scripts/Gear/UI/ForgeWindowUI/ForgeWindowUI.cs#L1163) executes a fixed rounded batch then waits with `WaitForSecondsRealtime`; it does not reconcile elapsed real time. Unlike this, [CauldronManager.TasteTick](../Assets/Scripts/Upgrades/CauldronManager.cs#L586) keeps an elapsed-time accumulator. Native tasting stayed approximately 100 rolls/s at requested caps 30/60/144 in repeated Editor tests.

   Consider an elapsed-time credit accumulator with a bounded catch-up budget for forging, preserving the exact upgrade-stop, lock, salvage and resource semantics. This is a timing correctness change as well as a performance change and must be explicitly approved for implementation later. Expected benefit: throughput closer to the configured rate across supported frame rates; it does not promise lower total crafting CPU. Risk: overspending, salvage rounding, skipped upgrade stops, burst work after suspension. Verify successful crafts, consumed resources, salvaged output and stopping item over equal real time at multiple caps and after pauses.

Local save/load results (median / worst milliseconds):

The first two capture timers include the save-state event; the synthetic-history capture timer restarts after constructing the detached 10000-record fixture, so it measures serializer entry rather than that fixture-construction cost. The frame capture includes the construction work. Do not interpret these timings as a perfectly isolated asymptotic benchmark. [SaveManager.CaptureAndWriteAsync](../Assets/Scripts/Blindsided/SaveData/SaveManager.cs#L219) serializes an immutable payload synchronously before dispatching durable I/O. The realistic developed capture was around 2 ms here; it is not the leading bottleneck. Local load completion includes the storage verification/deserialization task, not the whole UI/scene boot path. Direct tests do not establish normal autosave cadence; the supplemental coordinator experiment is reported separately. Live cloud upload behaviour remains unmeasured.

`ForgeAnalyticsService.Instance` and `BackgroundTelemetryProcessor.Instance` were absent in the live scene. Successful crafts increased Ivan XP and consumed resources, while `Forge.TotalCrafts` stayed at its baseline value. [CraftingService](../Assets/Scripts/Gear/CraftingService.cs#L113) only records telemetry when the optional analytics service exists. This is a **correctness/instrumentation discrepancy**: the save counter cannot be used to estimate craft throughput in this scene, and related statistics may be stale. Search found no scene/prefab reference to the analytics component's GUID. Wire-up and intended optionality should be reviewed before calling it a shipping regression. No proposed analytics threading concern is ranked as an active bottleneck when that service was not running.

Combat/task frame dependence remains a separate hypothesis unless supported by the paired measurements below. [HeroCombatController](../Assets/Scripts/Hero/HeroCombatController.cs#L336) permits at most one attack on a check and sets `lastAttack = Time.time`, discarding fractional overshoot. [ContinuousTask.Tick](../Assets/Scripts/Tasks/ContinuousTask.cs#L72) completes a task once its scaled timer reaches duration. These paths can quantise timing at low frame rates, especially at scale 4, but pathing, enemy health, travel, echo behaviour and different terrain all affect observed kills/tasks. A deterministic fixed-target attack/task benchmark is still needed before assigning an exact percentage of gameplay loss to either timer.

The map allocation timeline includes about 6.41 MB under `EchoController.Update > GetComponentNullErrorWrapper`. That marker is an Editor diagnostic path; do not extrapolate it to Player allocations. Forge `LateUpdate` also appears in the run allocation tree while its visual window is closed. The measured presence warrants visibility-aware UI investigation, but does not justify stopping the desired background crafting simulation.

After three rounds of 45-second, approximately 10 Hz UI navigation, the three retained checkpoints each had **87491 Unity objects**. Managed used memory at the ends of those windows was approximately 408.7, 410.0 and 415.5 MB, so neither a leak nor complete memory stability can be established from bytes alone. Editor compilation/profiler metadata, temporary fixtures, normal pools and managed collection timing affect memory. Collection counters 0/1/2 are recorded, but Unity's collector does not provide a useful independent generational breakdown here. Runtime pool and event-subscription observations supplement the counts; they are not a heap ownership analysis.

## Acceleration, longer-run and memory results

Native forge speed in this state is 20 crafts/s. Three Editor repetitions per cap produced:

| Requested cap, VSync off | Actual median frame interval | Successful crafts / real s |
|---|---:|---:|
| 30 | 33.6–33.7 ms | 16.00–16.21 |
| 60 | 15.9–16.1 ms | 18.50–18.52 |
| 144 | 9.3–9.7 ms | 18.90–19.11 |

This is a meaningful repeated scheduling difference (about 15–16% less throughput at the low cap versus the higher-cap case), independent of the stale save-total counter. The native asset rate is the same throughout. The 144 request did not achieve 144 rendered updates/s in this Editor workload.

Matched Farmlands settings, three 25-second windows each, tasting stopped:

| Loadout | Requested cap | Median frame interval range | Tasks / real s | Kills / real s |
|---|---:|---:|---:|---:|
| Four buffs, no Slipstream (scale 1) | 30 | 33.8–34.3 ms | 3.33–4.05 | 0.64–0.72 |
| Four buffs, no Slipstream (scale 1) | 144 | 14.7–19.0 ms | 3.44–3.84 | 0.72–0.76 |
| Same four plus Slipstream (scale 4) | 30 | 33.9–34.7 ms | 6.09–6.17 | 1.20–1.32 |
| Same four plus Slipstream (scale 4) | 144 | 26.6–27.8 ms | 7.84–8.12 | 1.60–1.64 |

Normal-speed task ranges overlap. Slipstream's lower-cap task ranges do not overlap the higher-cap ranges: about 6.13 versus 7.99 tasks/s on average, a roughly 23% difference. This is evidence of frame-rate-sensitive **whole-run** throughput under acceleration. It does not establish that the combat cooldown alone causes that difference, or that scale 4 should necessarily yield exactly four times as many completed tasks in a spatial, contention-limited workload. Independently seeded terrain and changing echo populations remain confounders; repeat a fixed workload in a Player before balancing around the percentage.

The five consecutive minute windows advanced Farmlands from about distance 109 to 4648, reaching the copied save's actual reaping threshold of **4645.245**. Frame p95 by minute was **39.8, 42.6, 43.9, 47.2 and 47.2 ms**; p99 and worst values are in the full table. Tasks/s fell 7.93 → 7.62 → 6.90 → 6.34 → 4.97, with different distance difficulty and echo counts, then reaping in the last window. The fifth window ends at time scale 1 after buffs clear; it is not a stationary scale-4 sample. The following `forced-death-transition` is therefore a redundant/no-op death probe, not evidence of a second fresh death. Fresh and mid-proxy `Haloween` runs separately incremented the death count, while `reap-threshold-transition` exercised a deliberately lowered threshold. These distinctions prevent transition labels being mistaken for successful coverage by themselves.

Pool observations covered 168 registered GameObject pools. After the broad map pass there were 1351 pooled instances; the repeated/long-run workload eventually reached 1442. During the five-minute run the total grew from 1422 to 1442 rather than exploding; inactive capacity persisted after returning to town. This is consistent with a modest high-water increase, not proof that every pool is bounded under arbitrarily long play. Global `EventHandler` subscription counts are present in each metadata file. The final closed-town p95 returned to about **13.4 ms** (versus post-map-town 12.2 ms); final managed used memory was about 514.8 MB versus 513.6 MB after the broad map pass. Total Unity allocated memory differed substantially across these checkpoints (about 3.85 to 4.96 GB), including the intervening Profiler capture and Editor/native allocations. That native increase remains unattributed; a memory snapshot/ownership diff is needed before declaring it either a game leak or harmless profiler retention.

Editor worst-frame values include some deliberate Pipeline script compilation/control activity, Profiler-window operations and fixture setup. For example, adding the focused map experiment interrupted the first native-forge cap-30 window. The raw maxima are preserved rather than silently censored, but isolated Editor maxima are not all game spikes. The repeated percentile shifts and attributable timeline slices carry more confidence. `raw_frame_max_including_boundary` additionally preserves the maximum before excluding the two metadata boundary samples.


## Rendered Development Player validation

[Player per-scenario table](profiling/2026-09-26/player-rendered/ScenarioResults.md) and [machine-readable summary](profiling/2026-09-26/player-rendered/summary.csv) contain 36 completed windows. ## Prioritised action plan and remaining unknowns

1. Address forge elapsed-time accounting as a correctness investigation first. Reproduce the three Player cap results with deterministic rolls/resources and stop conditions; implement only after separate approval. Preserve resource and upgrade-stop semantics as well as rate.
2. Prototype a narrower cauldron layout refresh boundary and repeat the clean rendered open/closed measurements. This has the clearest repeated Player CPU evidence. Include tier transitions, Infinity and localisation before accepting a gain.
3. Validate equipment-change churn in a Player and remove demonstrated hidden/repeated UI work in map and alter-echo panels. Keep background simulation running and verify freshly reopened displays.
4. Obtain coherent naturally progressed early/mid/late saves, run longer on Woods/Mines/River/Spooky, and make terrain/combat replay deterministic. Repeat normal/Slipstream caps before attributing throughput loss to an individual combat/task timer.
5. Profile generation slices and graph scans in a shipping-equivalent IL2CPP Development Player on weaker hardware. Pursue a generation redesign only if its Player hitch distribution justifies the risk.
6. Run a multi-hour stable-workload soak with managed/native memory snapshots before/after identical GC/scene states. Attribute the native-memory increase and inspect pool ownership and subscriptions beyond the global event hub. Stable global counts and modest pool growth do not prove leak freedom.

Further gaps: live cloud callbacks/network latency; repeated full Loading/Main scene reloads; every buff combination; exhaustive quest hand-ins, skill purchases, lock/rule combinations and tooltips; render draw/batch breakdown and GPU pass capture; statistically independent randomised-order experiments. Repetitions establish consistency for the principal UI/scheduler differences, not formal confidence intervals. Synthetic rates/history sizes are not presented as naturally reachable progression.
